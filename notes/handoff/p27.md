## E7, and Program P32's question applied to it

The specification is *bootstrap confidence-interval width against
evaluation-set size **on a public benchmark**; the size needed to resolve one
point.* P32's split settles the benchmark half before anything is computed:
**does the claim need external data, or is it a statement about the estimator?**

The width of a bootstrap interval on a proportion is a function of $(n, p)$ and
of nothing else, so a benchmark would supply exactly one number, $p$ — and
**$p$ sets the constant while $n$ sets the shape.** The shape is what E7 asks
for, so the sweep needs no download and runs at §2's own accuracy rather than a
borrowed one. Nothing in it is simulated either, and that is §2's own doing: it
had already established that on a proportion the bootstrap distribution *is*
$\mathrm{Binomial}(n, k/n)$ exactly, so every width is an exact percentile of
that binomial — no seed, and the same answer on every machine.

| items in the set | width, points | the interval, in items |
|---|---|---|
| 50 | 26.00 | 13 |
| 200 | 12.50 | 25 |
| 800 | 6.25 | 50 |
| 3200 | 3.12 | 100 |
| 12800 | 1.56 | 200 |
| 51200 | 0.78 | 400 |

Two things came out of it that the specification did not ask for and that are
the reason the frame is worth its length.

**The exactness is in the item column, not the points column.** Four times the
items halves the width, which is P25's rule measured rather than quoted — but
the halving is exact only in the spans, which double as whole numbers. The
points column is those spans divided by the set size and rounded, so dividing
two of *its* entries gives 2 to two decimal places and not 2 exactly. Quoting
the halving off the points column would have been a claim the page cannot
support; the frame says so and the script asserts the doubling on the integers.

**The crossing is not a single size.** The span moves one item at a time, so
near one point the width steps above and below it as the set grows — measured,
`width(31300)` is exactly one point, `width(31301)` is above it and
`width(31302)` below. A "smallest $n$" would therefore be an artefact of the
grid rather than a property of the method, and a bisection for it is a misread
instrument on a non-monotone function. What is committed instead is a round
figure, **about 31 000 items**, with the crossing bracketed at a tenth either
side, which is P06's rule for a quantity whose exact value is an artefact.

The one row that is not a halving is the smallest, and it fails upward: 50
items give 2.08 times the width of 200 rather than twice, because a span is a
whole number of items and on 50 items one item is worth two points. That is
§1's grid at its coarsest, and here it rounds the interval outward.

Three gates were added with them, and one of them found something. The
200-item row of the sweep **is** the interval §2 already prints, so it is gated
rather than resembled (`WIDTHS[200] == BOOT_HI - BOOT_LO`), and because the
frame now asks the reader to subtract the two endpoints, that subtraction is
checked on the *printed* forms as well — the endpoints carry one decimal and
the width carries two. The halving is asserted against a **derived** bound,
`150/n`, from the quantisation of each endpoint, rather than a tolerance chosen
so the check passes.

**Every assertion passed on the first run, which is what P27's own pass note
warns means only self-consistency — so the formulas were read against the
numbers anyway, and one was vacuous.** `SPANS[50] != 2 * SPANS[200] // 2`
compares 13 with 25 and cannot fail; what was meant is
`SPANS[200] != 2 * SPANS[50]`. Fixed, with the mistake recorded at the line,
because it is the class P01 and P05 both have entries for.

## Deliberately not done

- **No build of any format, and no page-level measurement.** Pagination is
  global and another session's merge voids it; the sync session owns the page
  table, the overfull multiset and the orphaned-cue walk. Note that this pass
  adds a frame with a six-row table in the middle of §2, so **every cue from
  §2 onward in P27 has been re-rolled** and the walk should expect it.
- **`figures/values/appf.tex` was left at `HEAD` first, and then regenerated —
  because CI is a hard gate on it.** The instruction for this pass was to leave
  it to the synchronising session, and `make verify` reporting it stale locally
  is indeed expected. What that instruction does not survive is a merge: the
  *Recompute every number* job fails on exactly that diff, and it runs first and
  gates the whole workflow, so the four PDF builds never ran at all on the first
  push. With the merge authorised, the file had to be current. It was
  regenerated **after** `origin/main` was merged in, so the counts describe the
  merged tree rather than a stale one: `appf.frames` 1864 → 1865, `appf.elicit`
  1028 → 1029, `appf.values` 1674 → 1688; `appf.elicit.pct` stays at 55.

  **The generalisable half is worth more than the fix.** A ledger that is
  "somebody else's to regenerate" and is *also* a hard CI gate cannot be both:
  every parallel session's first push is red for a reason that is nobody's
  defect, and the redness hides the page-level jobs behind it, which are the
  ones that matter. Either the numbers job should tolerate a stale `appf.tex`
  on a branch, or the instruction should be to regenerate it and let the sync
  session resolve the conflict. As it stands, a session that follows the
  instruction cannot find out whether its own change builds.
- **No trap added to `notes/02-grounding-and-traps.md`.** The obvious candidate
  is "an interval of one point on each model means a one-point difference is
  visible", which is real and which the new frame's last paragraph handles. It
  is not written to that file because trap numbers are appended sequentially
  and every parallel session would collide on the same lines. **It is owed.**
- **The issue's "No Quiz (Foundation-only)" checkbox is left false**, as P04,
  P14 and P24 to P29 each left it: every written program has a Quiz, and
  consistency with forty-six merged programs beats a checkbox already known to
